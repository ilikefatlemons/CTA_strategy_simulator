## 〇、这个仓库现在是什么

一个**逐根 K 线（非向量化）**的回测系统，目前跑在 **59 个中国商品期货品种的 1 分钟数据**上。

三个策略共用一套数据层、一套时段纪律、一个终端窗口（`python -m src.run_v3_rbreaker_chart`，右上角三向互斥切换）：

| 策略 | 属于 | 方向 | 出场 |
|---|---|---|---|
| Archive-Pullback（多周期回调） | lineA | 顺势 · 日线定方向，小周期等回调 | 入场定死固定止损，止盈后换吊灯线 |
| R-Breaker 突破 | lineB | 顺势 · 站上 Bbreak / 跌破 Sbreak | 追踪止损 + 时段末强平 |
| R-Breaker 反转 | lineB | 逆势 · 触及 Ssetup 武装后破 Senter | 追踪止损 + 时段末强平 |

**必须先知道的一件事**：v3.0 换的是**数据底座**（美股 ETF 5 分钟 → 中国商品期货 1 分钟），不是换策略。lineA 的回调逻辑被**整套移植**过去——周期角色 5m/15m/30m/2h → 1m/5m/30m/1d，策略逻辑一个字没改，`tests/test_pullback_v3_vs_v21.py` 对着未改动的 v2.1 引擎逐笔判等。所以**两条线都是活的**，不要把 v2.x 当成被废弃的东西。

## 二、文件命名规范

```
版本 - 类型 - 内容.md
 │      │      └── 中文，说清这份文档回答什么问题
 │      └── 四个大写字母，见下表
 └── 写于哪一版（在「参考资料」与「data/」下表示「写于」，不表示「属于」）
```

例：`v3.0-PLAN-R-Breaker突破实施方案.md`

`docs/`、`data/`、`report/` 三处统一用这套命名。**目录表达「属于哪一块」，文件名表达「写于哪一版 + 是什么性质」**，两者不重复。

**不套用此规范的文件**：本文件 `README.md`、根目录 `CLAUDE.md`（Claude Code 的工具约定文件，文件名固定）、以及脚本与证据 CSV。

## 三、八个类型码

排列顺序就是这个项目一轮迭代的实际节奏：调研 → 讨论 → 枚举 → 计划 → 落地 → 挑错 → 记账 → 汇报。

| 码 | 含义 | 判据（用来 2 秒内决定选哪个） |
|---|---|---|
| **RSCH** | 外部研究 | 内容来源在仓库**外**：文献、交易所制度、别人的策略 |
| **MEMO** | 讨论记录 | 内部人的对话原文，还没成型（boss 讨论、会议记录） |
| **ENUM** | 枚举编目 | 把可能性**穷举成编号目录**，不做取舍 |
| **PLAN** | 计划设计 | 写在动手**之前**：要做什么、怎么做 |
| **SPEC** | 现状规格 | 系统**现在**是什么样，逐层走查 |
| **DIAG** | 审计诊断 | 找问题，输出**问题清单** |
| **LEDG** | 执行台账 | 逐条记录**改了什么、结果如何** |
| **BRIF** | 汇报精简版 | 受众是**别人**，删掉实施细节。**一律放 `report/`，`docs/` 里不留 BRIF** |

三对容易混的边界：

- **PLAN vs SPEC** —— 动手前 vs 动手后。同一套逻辑写两遍不是冗余：`v2.0-PLAN-全链路严谨设计图纸` 和 `v2.0-SPEC-全链路数据流` 之间的**差值本身就是信息**（哪些设计没落地）。
- **DIAG vs LEDG** —— DIAG 出问题清单，LEDG 记修复结果。v2.1 那批文件正好是这一对的完整示范。
- **RSCH vs MEMO** —— 公开知识 vs 内部对话。boss 与 Gemini 讨论出的公式泛化提案是 MEMO，不是 RSCH。

## 四、四个顶层目录，四条不同的分支轴

```
TradingApp/
├── README.md      本文件
├── CLAUDE.md      Claude Code 工具约定（⚠ 内容已过期，见 §八）
│
├── docs/          知识与设计 —— 写给做事的人。分支轴 = 策略线
├── src/ tests/    代码与测试
├── data/          数据本体 + 排查脚本 + 排查证据。分支轴 = 数据层
└── report/        汇报产物 —— 写给老板/同事。分支轴 = 对齐 data 的层
```

三处目录**都不再按版本号分**。原因是版本号在三条坐标轴上不同义：`docs` 有 v1.0~v4.0，`data`/`report` 多出 v3.1/v3.2（纯数据治理，没有对应的策略文档），`src` 根本没有版本标记。按版本号做目录，新人第一个疑问永远是「v3.1 的文档呢，是丢了还是没有」。

### docs/ —— 分支轴是「策略线」

```
docs/
├── 00-总览/                    两条线的公共出发点
├── 01-平台层/                  两条线共用：数据层纪律、中国期货特殊规则
├── 02-lineA-多周期回调/         策略线 A
│   ├── A1-初稿-Archive美股策略照搬入中国期货1m/
│   ├── A2-策略多样性探索-多周期回调/
│   └── Archive-美股测试/        （旧 A1/A2，美股 ETF 时代）
│       ├── Archive-美股-v1.1/
│       └── Archive-审计与修正-v2.0~v2.1/
├── 03-lineB-R-Breaker/         策略线 B
│   ├── B0-原理与出处/
│   ├── B1-初稿-拆分成两个策略+时段/
│   └── B2-策略多样性探索-R-breaker/
└── 04-参考资料/                与线、与版本都无关的领域知识
```

**另有 `obsidian/`（不在 docs/ 下）** —— lineA 的**设计层**，一个 Obsidian vault：25 个模块位、49 个中文参数、十节模块契约、求值顺序与无未来函数审计表。⚠ 它的「模块可独立互换」前提正在被重新审视，见 §八 缺口 6。

**lineA 的分支轴是「阶段」** —— 同一套信号逻辑被反复审计、移植、重构，是一条时间轴：

| 分支 | 阶段 | 干了什么 |
|---|---|---|
| **Archive-美股-v1.1** | 美股 · v1.0~v1.1 | 逻辑在这里定型：2h 定方向 → 30m 回调确认 → 5m/15m 触发。数据是 Alpaca 复权 5 分钟，12 个美股 ETF |
| **Archive-审计与修正** | v2.0~v2.1 | 逻辑一个字没改，全部精力用来**挑自己的错**：A1–C22 错误清单 → 逐条修 → 逐条记录前后指标。`DIAG → PLAN → LEDG` 这条链在这里跑完了一整轮 |
| **A1-初稿** | 照搬入中国期货 1m · v4.0 | 结论是「失效不是条件太严，是条件之间的结构关系有缺陷」，并枚举了 82 个候选调整方案。⚠ **移植那一步本身仍无文档**，见 §八 |
| **A2-策略多样性探索** | v4.0 | 把「回调再入场」拆成 `板块 → 逻辑 → 措施` 三层树，11 个板块 + 自洽四轴，产出**四条内部自洽完整链** |
| **A3-单个自洽策略实施+改进** | v4.0 | 当前在做。`goal.md` 是规格，代码已落地（`src/*/lineA_03*`，入口 `python -m src.run_lineA_03`）。只做 AU 一个品种 |

**lineB 的分支轴是「变体」** —— 三个并列的东西，不是先后关系：

| 分支 | 内容 |
|---|---|
| **B0** 原理与出处 | 六线公式（Bbreak/Ssetup/Senter/Benter/Bsetup/Sbreak）的定义与出处声明，附与 Turtle 的对比 |
| **B1** 初稿-拆分成两个策略+时段 | **突破**（顺势，读两条线）、**反转**（逆势，读四条线）、**时段模式**（5 种时段划分 × 2 策略 = 10 种组合）。三个文件放在一起，因为它们共用同一套执行纪律、初始止损距离逐字节相同，拆开就看不出这层对称性 |
| **B2** 策略多样性探索 · v4.0 | 当前在做。突破半边与反转半边逐品种净收益相关系数仅 **+0.145**（近乎正交），这是把它们合成的唯一硬理由。B2 枚举了 6 类耦合方式，并给出标准化测试规范（STD-TEST） |

### data/ —— 分支轴是「数据层」

编号**不是**血缘顺序，而是「跨层打头，然后按加工程度：pkl → txt → level-1」。越靠前越是回测实际在读的。

```
data/
├── 00-跨层/                 txt ↔ pkl 逐合约对账（装不进任何单层）
│   ├── compare_layers.py
│   ├── v3.2-SPEC-三层数据已知事实.md   ← 三层 schema 与已知缺陷的权威表
│   └── 对账证据/
│
├── 01-pkl层/                二级数据：主力连续 + 复权因子
│   ├── all_symbol_min_full_main_close_k_1.pkl    79 品种，6,628 万行（5.96 GB）
│   ├── 一次排查/
│   │   ├── clean_1m/         清洗后 59 个 parquet + _manifest.csv ← **回测直接读这里**
│   │   ├── check_db/、排查脚本/、排查证据/
│   │   ├── v3.0-SPEC-数据质量排查判据.md
│   │   └── v3.0-LEDG-品种筛除日志.md
│   └── 二次排查/
│
├── 02-txt层/                通联日频 txt，1 分钟 K 线
│   ├── 原始数据/             3,990 个 future_pricemin*.txt（含 weekend/ 10 个）
│   ├── 排查脚本/  排查证据/
│   └── v3.2-DIAG-OHLC零价行分析.md
│
├── 03-level-1层/            最原始：逐笔快照。探查阶段，数据尚未落地
│
└── Archive-美股数据/        lineA v1.0~v2.1 的数据，与期货三层无关
    └── raw/                  12 个 *_5m.csv（Alpaca 复权 5 分钟）
```

**为什么是四个而不是三个**：`00-跨层` 装不进任何单层——它的全部价值就是验证 pkl 是否忠实于 txt。

**代码里的路径只有一个真源：`src/data/paths.py`。** 别处一律 import，不许抄字面量。这次重组曾同时打断三处硬编码路径，而 6 个测试文件 guard 在 `os.path.exists(CLEAN_DIR/...)` 上于是**静默跳过**了 133 个测试（`pytest -q` 一直是绿的）。

### report/ —— 分支轴对齐 data/ 的层

```
report/
├── 数据/                     （编号与 data/ 对齐）
│   ├── 00-跨层/              v3.2-BRIF + v3.2-DIAG + 明细/ 28 个 csv
│   ├── 01-pkl层/             一次排查/v3.0-DIAG、二次排查/v3.1-BRIF、明细/ 8 个 csv
│   ├── 02-txt层/             v3.1-BRIF（精简）+ v3.1-DIAG（完整）+ 明细/ 19 个 csv
│   └── 03-level-1层/         v3.2-DIAG-Level1数据探查发现.md
└── 策略/
    └── v4.0-BRIF-回调策略结构诊断与修正原则.md
```

`report/` 是**汇报产物的唯一落点**——凡是 BRIF 类文档都放这里，`docs/` 里不留。

**关于「多一层 `数据/` 会不会太深」**：不会。原来最深是 `report/v3.2/明细/二级层/xxx.csv`（4 层），现在是 `report/数据/02-txt层/明细/xxx.csv`（还是 4 层）。新增的 `数据/` 是从 `明细/二级层/` 里换出来的——层级提到上面之后，明细内部就不用再按层分了。

`策略/` 暂不按 line 再分，只有一个文件，分了就是空壳。
