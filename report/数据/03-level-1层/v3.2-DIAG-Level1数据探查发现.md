# v3.2 Level-1 数据探查发现

**对象**：`qtg_data.tbl_future_book_l1`（外部 SQL Server 表，**不在本仓库内**），逐笔行情
**方法**：拿 raw 层《v3.1-DIAG-原始数据质量报告.md》的 P0/P1 问题清单，逐条到 Level-1 上复核，判断每条缺陷是**行情源固有**还是**下游加工引入**
**结论**：Level-1 是目前唯一能给「这个错是谁造的」下判决的层。已复核 6 条 —— **2 条证伪**（P0-1、P0-6，源头没有 → 下游加工引入）、**3 条上推到源头**（P0-2、P0-4、P1-9）、1 条部分可核（P0-3）
**状态**：**探查阶段，一行数据都没落地到仓库。** 全部结论来自手写 SQL 点查，样本是**单日单合约**级，不是全量扫描
**工作底稿**：`data/03-level-1层/v3.2-DIAG-Level1数据探查发现.md`（原始 SQL 笔记，本文是它的正式版，底稿保留不动）

## 0 先记住三件事

### 0.1 Level-1 的 OHLC 和通联分钟 K 的 OHLC 不是同一个东西

通联给的是**那一分钟**的 OHLC；Level-1 快照里的 `open_price / highest_price / lowest_price` 是该合约**当日累计**的开、最高、最低。

**直接拿去逐字段比对会全错。** 这是本层第一条、也是最容易踩的坑。

### 0.2 Level-1 → 通联 1 分钟 K 的合成算法未知，甚至不能确定是「合成」出来的

P0-3 的复核里，同一根 bar 的 `volume` **完全吻合**，但 `high` 一个给 8209、一个给 8207。量对得上、价对不上，说明两者至少不共用同一条价格聚合链路。

> **因此 Level-1 只能当仲裁旁证，不能当 raw 的逐字段对账基准。**
> 它能回答「这个现象在源头存不存在」，回答不了「这一根 bar 的四个价对不对」。

### 0.3 发布频率是混合的

实际看数据发现：**一部分是逐笔推送，一部分按固定间隔推送，两者混在一起**，具体怎么分类尚未整理（也不影响当前结论）。

所以**不能假定「每 N 毫秒一条」**，任何按固定频率做的重采样或补点都要先验证。

## 2 逐条复核

### 2.1 P0-1 有夜盘品种缺 09:00 日盘集合竞价 —— **不成立，源头不缺**

```sql
SELECT trading_day, exchange_id, exchange_time, id, instrument_id,
       open_price, highest_price, lowest_price, close_price
FROM qtg_data.tbl_future_book_l1
WHERE trading_day >= 20241231 AND trading_day <= 20250103
  AND (exchange_time > '08:00:00.000' AND exchange_time < '09:00:01.000')
ORDER BY trading_day
```

**结果**：不缺集合竞价，08:55–09:00 之间是有数据的。

**对下游的含义**：raw 层「39 个品种在 2023-05-26 后的 718 个交易日里，27,436 个（品种×交易日）组合中有 09:00 的 = 0」这个现象，**不是交易所没发，是取数或分钟 K 构造环节把它丢了**。提需求时应写「恢复」而不是「补充」。

**遗留**：bar 具体怎么从 Level-1 合成到通联 1 分钟 —— 不知道，甚至怀疑不是合成的（见 §0.2）。

---

### 2.2 P0-2 节假日前后的夜盘 —— **源头是真实成交，被下游换成了 padding**

```sql
SELECT trading_day, exchange_id, exchange_time, id, instrument_id,
       open_price, highest_price, lowest_price, volume, turnover, close_price
FROM qtg_data.tbl_future_book_l1
WHERE trading_day = 20260213
  AND (exchange_time > '15:00:00.000')
  AND instrument_id = 'au2603'
```

**结果**：
- 节假日**前**夜盘有 "padding"，且**只到当日结束、不延到第二天**
- 但 Level-1 行情里**是真实数据，有成交量和价格**
- 节假日**后**没有夜盘

**对下游的含义**：这是本次复核里方向最明确的一条。raw 侧那 2,488,070 根零成交 padding K 线，对应的时段在源头是**有真实成交的**。所以下游不是「把不存在的时段填满了」，而是「**把真实成交换成了平 K 线**」——性质更严重，且意味着这批真数据是可以取回来的。

---

### 2.3 P0-3 节后 01:00 / 02:30 那根 K 线 —— **量对得上，价对不上**

raw 层的案例（AG2506，2025-05-06 劳动节后首日）：

```
02:29  8182  8182  8182  8182  vol=0        <- padding，= 前收盘
02:30  8156  8156  8156  8156  vol=12226    <- 平 K 线 + 大成交量
09:01  8158  8207  8158  8205  vol=14998    <- 日盘开盘 8158
```

```sql
SELECT trading_day, exchange_id, exchange_time, id, instrument_id,
       open_price, highest_price, lowest_price, volume, turnover, close_price
FROM qtg_data.tbl_future_book_l1
WHERE trading_day = 20250506
  AND (exchange_time > '02:29:00.000')
  AND instrument_id = 'ag2506'
```

**结果**：
- `volume` **完全吻合**
- OHLC 略有偏差：09:00 结束后那根的 `high`，Level-1 给 **8209**，通联给 **8207**
- 其余数据**无法查证，因为不知道怎么合成的**

**对下游的含义**：这条同时是 §0.2 那个判断的证据来源。量能对上说明两层看的是同一批成交；价对不上说明价格聚合口径不同。**在搞清合成算法之前，任何「Level-1 vs raw 逐价比对」的结论都不可信。**

---

### 2.4 P0-4 郑商所集合竞价 K 线不是平 K 线 —— **行情源固有**

```sql
SELECT trading_day, exchange_id, exchange_time, id, instrument_id,
       open_price, highest_price, lowest_price, volume, turnover, close_price
FROM qtg_data.tbl_future_book_l1
WHERE trading_day = 20260710
  AND (exchange_time > '00:50:00.000')
  AND instrument_id = 'TA609'
```

**结果**：**Level-1 数据给的 OHL 就不是相等的。**

**对下游的含义**：raw 层观察到的「上期所/大商所/能源中心 21:00 平 K 线比例精确 1.000，郑商所常年 0.30–0.40」不是通联加工出来的差异，源头就长这样。这条在《v3.2-DIAG-两层数据质量整改清单.md》里已经列为**【需书面答复】**而非修数据项——本次复核支持这个定性：要问的是郑商所竞价 K 线的**时间区间定义**，不是要谁去改数。

---

### 2.5 P0-6 元旦被伪造成完整交易日 —— **不存在**

**结果**：Level-1 上查不到。

**对下游的含义**：2024-01-01 与 2025-01-01 那两批（raw 侧 197,978 根 + 216,102 根、vol 全 0）是**下游凭空造出来的**，源头没有任何对应记录。这条和 P0-1 一起构成「源头干净、下游脏」的两个实例。

---

### 2.6 P1-9 首笔成交 OHLC=0 —— **在 Level-1 上重现**

**结果**：**OHLC=0 问题在 raw data 上重现**（此处 raw 指 Level-1 原始行情）。

**对下游的含义**：这是本次复核里唯一一条把 raw 层最厚的缺陷（438,756 行 / 8,497 个块 / 种子命中率 1.0000 / 传染放大 33.2 倍）直接上推到行情源的。**通联的分钟 K 构造器确实有「首笔成交没正确初始化 OHLC」的 bug，但它拿到的输入本身就带 0。** 整改要求应该两边都提。

## 3 Level-1 独有的三个问题

### 3.1 重复时间戳

```sql
SELECT trading_day, exchange_id, exchange_time, id, instrument_id,
       open_price, highest_price, lowest_price, volume, turnover, close_price
FROM qtg_data.tbl_future_book_l1
WHERE trading_day = 20260203
  AND (exchange_time > '15:00:00.000')
  AND instrument_id = 'AU2603'
ORDER BY trading_day
```

**结果**：`exchange_time = 19:02:54.500` **重复**。

**含义**：任何以 `(instrument_id, exchange_time)` 为主键的落地设计都会撞键。落地前必须先决定去重口径（保留哪条、还是都留并加序号）。

### 3.2 含 efp 合约

Level-1 里有 **efp 合约**（期转现）。**不要引入。** 下游 raw 与 pkl 都没有这类记录，引入会凭空多出一批下游对不上的合约。

### 3.3 时间戳落在可交易时段外

例：`20241231` 的 `a2501` 出现 `18:32:41.000`。18:32 既不在日盘也不在夜盘。

**含义**：落地时不能拿 `exchange_time` 直接切时段，必须先过一遍交易日历 + 品种时段表。

## 4 待补证据（口头记录，SQL 尚未跑）

以下两条是看数据时直接观察到的，**尚未写成可复现的 SQL、也没统计范围与量级**，先记在这里免得丢失：

- **每天 06:00 前后与 18:00 前后有数据，且 OHLC 全部等于 0。** 这两个时刻都在所有交易时段之外，怀疑是系统心跳、日切或状态快照。需要确认：是全品种还是部分品种、是不是每天都有、`volume` 是否也为 0。
- **白盘、夜盘收盘后会有尾数据陆续到达**，例如 15:06、15:08 这样的时间戳。需要确认：是收盘后的结算态推送、还是延迟到达的成交回报；落地时应当截断还是保留。

这两条如果坐实，**会直接影响「Level-1 落地时怎么切时段」的设计**，优先级不低。

## 5 已知缺口

1. **Level-1 → 通联 1 分钟 K 的合成算法未知**，甚至不确定是否为合成。这是数据端的**答复项**，不是修数据项。在拿到答复前，Level-1 的价格字段不能用于对账。
2. **一行数据都没落地。** 现有全部结论来自单日单合约的 SQL 点查，样本量极小，不构成分布。按仓库的方法论要求（STD-TEST），落地后所有结论都要重新以「分布 + 样本量 n」的形式给出。
3. **发布频率混合（部分逐笔、部分定频）未分类。**
4. **Level-1 与 pkl 从未直接比对过。** 目前只有 Level-1 ↔ raw、raw ↔ pkl 两组，三层闭环没做。
5. **本层没有排查脚本、没有排查证据文件**，`data/03-level-1层/` 下只有一份笔记，不符合其余两层 `原始数据/ + 排查脚本/ + 排查证据/` 的三件套约定。
